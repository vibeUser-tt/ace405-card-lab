# ACE405 建筑竞标实验室

学生与有限状态机对手竞标同一建筑设计委托的 Web 卡牌原型。原来的“余烬之塔”两场打怪系统已替换为建筑性能指标、措施卡、功能卡和单人对抗流程。每个关卡对应课程周次与不同的目标函数；没有学生之间的对战。

## 运行

需要 Node.js 20.19+ 或 22.12+。

```powershell
cd ace405-card-lab
npm install
npm run dev
```

打开终端给出的本地地址，通常为 http://127.0.0.1:5173/。运行 `npm run build` 构建静态网页；运行 `npm test` 执行规则测试和固定种子模拟。桌面与手机浏览器交互测试脚本为 `node scripts/ui-smoke.mjs`，需本地 Vite 服务、Playwright 与 Chrome。

## 发布到 GitHub Pages

这个 `demo` 目录是独立仓库的根目录。仓库的 `main` 分支推送后，`.github/workflows/deploy.yml` 会构建并发布多个独立版本。新版位于 `/v2/`，原来的 `/` 与 `/v1/` 固定保留提交 `db7f5ea70d0be71dad2ff95904717fc7448697e7` 的旧版。版本配置位于 `release.json`，打包由 `scripts/package-pages.mjs` 完成，最终发布目录为 `.release/site/`。Vite 使用相对资源路径，因此普通项目仓库和 `<用户名>.github.io` 仓库都可使用。

1. 在 GitHub 创建空仓库，不勾选初始化 README、`.gitignore` 或 License；将本目录推送到 `main`。
2. 在仓库 **Settings → Pages → Build and deployment → Source** 选择 **GitHub Actions**。
3. 等待 **Actions → Deploy to GitHub Pages** 成功后，从 Pages 设置页打开网站。普通仓库地址为 `https://<用户名>.github.io/<仓库名>/`。

GitHub Pages 是公开网页。当前游戏记录只保存在访问者自己的浏览器中，不会跨设备同步。

## 3D 战场与手机适配

主界面采用单个 Three.js Canvas。第二版使用 Blender 制作的现代建筑、24 张正式措施组件、门、人物，以及扩大的外圈步道、远移的树木、花池、长椅、矮灯、自行车架和分类垃圾箱，双方复用 GLB 与贴图资源。P1/P2 替换为真实浅进深／中庭主体；P3/P4 打开屋顶展示反射面／空间重排，屋顶设备随布局调整安装位置。方向光保持固定朝向；建筑旋转、门和人物移动时实时更新阴影。后台暂停场景更新；减少动态效果偏好下人物和门保持静止。

建筑使用 Cycles 烘焙的颜色贴图与柔和环境光贴图。环境光贴图不含太阳、门或人物，记录局部稳定的环境照明与遮蔽；网页使用第二套 UV 采样，并排除重复的半球环境照明，再叠加实时太阳光。单独 AO 作为诊断与后续备用贴图，不重复乘到已含遮蔽的环境光上。玻璃为不透明的风格化颜色，没有实时反射、折射或多层透明。Blender 的 Diffuse 材质对应网页的 Lambert 材质，两端使用 AgX。网页材质直接采样 `Art/export_display_lut.py` 通过 Blender 输出的 57³ 色彩校准表，替代默认 AgX 近似曲线对饱和蓝绿的偏差；约 1.48 MB、一次材质内 3D 纹理采样，不增加全屏后处理或渲染通道。

人物的 `Walk` 动作由 Blender 制作并通过 GLB/NLA 导出；每栋两人，身高约为门高的 79%。网页驱动与门同向的外圈绕行、门前停下、等待门完全打开、进屋、随机停留 6–16 秒再出来；门口一次只接待一人，另一人避让。建筑、人物及动画播放器保持存活，出牌只替换当前组件与状态特效，避免动作归零或重复加载资源。

v2.1 新增长椅休息：人物经过外侧长椅时随机决定是否休息，依次走近、转身、小步后退、坐下，停留 7–20 秒后起身并回到原步道。每栋建筑同时只允许一名人物预留或使用长椅，从走向椅子到离开通道都保留占座；另一人继续散步，在进出通道处避让。坐下者等待通道清空再起身。两张椅子都能使用，离座后有 35–70 秒冷却。

座面、入座路径和人物肢体尺寸共用 `src/pedestrian-layout.json`，Blender 导出 `Seat_0`／`Seat_1` 锚点和膝、踝关节。网页用双骨段逆运动学驱动坐下、起身，脚保持贴地、臀部对齐座面；椅前铺装与路缘开口为后退入座预留净空。坐姿使用原有受光和阴影，不增加灯光或额外渲染通道。

### 美术资产与参考验证

- 当前资源位于 `public/assets/modern-v2/`。`building.glb` 将场地、建筑、屋顶分开；`citizen.glb` 包含 Walk；`components.glb` 包含全部 24 卡与两套主体布局，安装参数和动画轴见 `components-manifest.json`。
- 可编辑源已随仓库完整保存： `Art/modern-building-v2.blend`、`Art/components-v2.blend`，四种组合另存为 `modern-cards-v2-1.blend` 至 `modern-cards-v2-4.blend`，坐姿参考为 `modern-seated-v2.blend`。打开基础 blend 后运行 `Art/render_seated_v2.py` 可重新生成坐姿场景和原生参考图。
- `Art/pack_sources.py` 将贴图打包进全部 `.blend` 源文件；`Art/export_display_lut.py` 导出网页色彩校准表。随仓库提供的源文件可独立打开，无需原工作区路径。
- 基础制作：后台 Blender 运行 `build_modern_v2.py -- build`，再打开生成的 blend 依次运行 `-- bake`、`-- variants`、`-- render-back`。`build` 需 `--factory-startup`。后台都加 `--python-exit-code 1`，防止 Python 异常被误报成功。
- 组件制作：`build_components_v2.py` 默认生成组件，再打开 `components-v2.blend` 依次运行 `-- bake-layouts`、`-- bake-cards`。完成后重跑基础 `-- variants`，其中浅进深场地烘焙依赖布局资产。`render_components_v2.py -- 1` 至 `-- 4` 生成四组原生 Blender 参考图。
- 颜色统一由 `Art/palette-v2.json` 管理：暖米色主体、蓝青色玻璃与金属、鲜绿植物和暖色人物。旧版灰感主要来自低饱和源色；此次修改源材质并重烘焙，不使用全屏饱和滤镜。Blender 与网页仍保持相同 AgX 和固定光照。
- 静态组件具有自己的环境光贴图；可动百叶、风机、通风口保持实时受光，未被写入静态遮挡。地面按浅进深／普通／开屋顶状态选择对应环境图，防止留下旧建筑暗影；玻璃仍无实时反射或折射。
- `/?renderReview` 支持正反机位、四种六卡组合、全部单卡选择和人物动画。组合参数例如 `?renderReview&cards=W2,I2,S2,P2,M2,T2`，坐姿近景为 `?renderReview&seated`。固定机位可切换 Blender 原始图进行目检。
- `node scripts/render-v2-audit.mjs` 核对实际 GLB、lightmap/UV、人物比例、15 种行走／进出／休息状态、24 卡与布局切换，并保存真实浏览器截图。`python Art/compare_renders.py --version 2`、加 `--back`、`--cards 1` 至 `--cards 4` 或 `--seated` 对照七组原始图；坐姿前景 SSIM 为 0.921。0.90 为可复现的辅助技术门槛，不等同于主观美术百分比。
- `node --experimental-strip-types scripts/pedestrian-audit.mjs` 累计模拟 80 分钟，验证步道范围、人物间距、门扇净空、静止等待、随机室内／长椅停留、单人占座、反复进出和休息。
- `node scripts/seating-browser-audit.mjs` 检查实际导出人物与椅子、路缘等场景网格；覆盖两张椅子的完整进出过程、安装组件和旋转建筑。1,078 个采样帧、100,176 次三角形候选检查未检测到穿插，脚与座面误差小于 0.001 mm；这是这些路线和采样帧的验证结果。
- `node scripts/render-v2-performance.mjs` 测量双建筑各装满六卡（含活动百叶、中庭、通风口）、共四人的本机开销。1440×900、Intel Arc、Direct3D11 实测约 30 fps（静态交互时上限 30）、167 次绘制，含阴影约 20.9 万三角形。手机视口测试只验证布局与操作，不代表真机帧率。

Y 轴朝上。左右拖动任一建筑区域时，只旋转该建筑的 Y 轴；横向位移除以该侧区域宽度再乘 2π 得到角度变化，竖向位移不改变角度。鼠标与触摸共用 Pointer Events，拖动超过 5px 后不会再触发装置点选。两边朝向独立保存，出牌更新组件和横竖屏切换均保留朝向。安装、反制、增益和护盾的粒子目标每帧从部件局部坐标转换到当前世界坐标，飞行中继续旋转也能跟随；裂纹、护盾网格与气流随建筑一起转动。

安装牌触发装配粒子；反制从手牌位置飞向目标部件，命中后出现碎片、冲击环和本轮裂纹标记；护盾显示保护网格。模型是教学示意，性能指标仍由规则模型计算。点击 HUD 可查看原始值、评审值和权重；点击建筑装置可选取增益或反制目标。

布局根据 `visualViewport` 的实际宽高调整。窄长卡牌下方是结束回合；操作条在手牌上方，短横屏时移到手牌右侧：装置牌分别用“装到自己”和“反制对手”直接执行，不需要第二次确认；不可用时按钮变灰并显示体力、预算、次数、同名装置等原因。功能牌使用“打出这张牌”。槽位上行显示装置名，下行始终显示“窗 / 围护 / 遮阳 / 平面 / 材料 / 系统”，空槽显示“未安装”。同槽位换装按钮显示“替换现有装置”，手牌标题旁预告旧→新及预算变化，模型播放拆卸碎片与安装粒子。优化、干扰和护盾通过点击建筑槽位选择措施，可用槽位呼吸高亮，选中后以金色勾选标记显示；只在操作条选择指标。切换措施会清空指标选择，取消或成功出牌后清除高亮，减少动态效果偏好改用静态高亮。灰牌原因、路线和选目标提示统一在“手牌 · 第 N 轮”旁显示。聚焦筛选和保留备选仍直接点选手牌，不打开面板。短横屏按 HUD 与槽位之间的可用空间调整模型显示，避免遮挡。窗口调整、旋转和浏览器工具栏改变可用高度时会重新计算，并保留当前局与所选目标。界面预留刘海与底部手势安全区。

32 张牌均有成功出牌反馈。玻璃、围护、遮阳、布局、材料与系统的安装粒子使用不同形状和颜色，装置从目标位置组装出现；反制命中对应部件。八种功能牌分别显示抽牌、弃抽、体力、保留、增益、干扰、强化与护盾反馈。保留标记与待用反制强化持续显示，粒子落点按出牌后布局计算；未满足条件的牌不播放成功特效。减少动态效果偏好会关闭飞行粒子，保留文字结果。

`npm run test:ui` 要求本地 Vite 服务、Chrome、Playwright 与支持 TypeScript stripping 的 Node（当前测试为 Node 24）。视口覆盖 568×320、667×375、740×320、844×390、932×430、1024×768、1440×900，以及 360×640、390×844、430×932；检查按钮位于手牌上方或短横屏的右侧，且不与手牌或建筑区域相交、操作按钮在屏内、旋转后选择不丢失、模拟安全区、32 张牌特效及全部模型变体。`complete-games.mjs` 用触控事件在 667×375、844×390、390×844 各从开局打完两局，覆盖安装、同槽换装、同名反制、功能牌与完整结算。这些固定种子整局样例用于交互回归，不是平衡性胜率估计。测试使用桌面浏览器模拟触控视口，实际手机 GPU 性能及 iOS 应用内浏览器仍需真机体验。

## 卡牌游戏 UI（第二版）

全界面采用蓝色立体面板、深色描边、奶油色卡面和金色行动按钮，覆盖选关、HUD、手牌、操作区、牌组、规则与结算。24 张措施牌插画由 Blender 真实资产渲染，位于 `public/assets/modern-v2/cards/`；八张功能牌使用本地 SVG 游戏图标，交互效果各不相同。插画可由 `Art/render_card_icons_v2.py` 复现。

竖屏且宽度小于 650px 时，放大显示当前建筑，顶部标签在双方之间切换；两边分数与预算继续同时显示，四项指标与安装槽位随当前建筑切换。增益、反制、护盾目标选择会自动切到对应建筑。横屏显示两栋建筑，短横屏将操作按钮放在手牌右侧；其他尺寸的操作按钮位于手牌上方。朝向、人物状态和本局选择在切换查看与屏幕旋转时保留。

主题集中在 `src/game-skin.css`，图标在 `src/GameIcon.tsx`。`scripts/ui-skin-audit.mjs` 截取选关、战斗、选牌、规则、牌组和结算，覆盖桌面、竖屏和横屏；另由完整 UI 回归验证触控、目标选择、保牌、换装和完整对局。皮肤不改变课程规则或性能指标。

## 每局如何玩

1. 选择课程关卡，阅读四项指标门槛、预算上限与公开权重。
2. 每轮抽 5 张牌、获得 3 点基础体力；安装至多 1 张措施、反制至多 1 次、使用至多 2 张功能牌。体力牌可将本轮体力提升到 5。
3. 措施卡可以装到自己的方案。同槽位允许换成不同装置：消耗新牌体力，占用本轮一次安装；旧装置永久移出本局，不进入弃牌堆，其增益、压制和护盾同时清除。相同装置不能重复安装。预算按最终方案重新计算，扣掉旧装置并加入新装置，同时重算联动。对手遵守相同规则，并能通过换装应对压制。如果对手已经安装同名措施，也可以消耗这张手牌反制对手一个**有正向边际收益的指标**。同名反制削减该收益 50%，通用反制牌削减 25%。反制牌从本局移除。
4. 状态机在学生行动前公开本轮意图。它只使用自己的手牌、双方公开方案和公开目标函数，按 SECURE → PRESSURE → BUILD → REFILL 的优先级作决策。
5. 结束回合时，对手执行行动，然后双方同时评审。先通过全部四项性能门槛与预算门槛的一方获胜；同轮都通过时比较公开加权分、再比较预算；仍相同则平局。
6. 结算页展示最终结果与得分，不展示逐轮记录；按本关开放槽位并排列出“你的方案”和“对手方案”的最终装置、未安装槽位、预算、永久优化及结算当轮压制；已拆除的装置不列入最终方案。课程关卡均可从入口选择；本地浏览器会记住各关卡最快的**达标**轮数。平局仍表示学生方案达标，但不算竞标胜利。游戏成绩不替代课程作业评价。

八种功能牌分别负责抽牌、弃抽、补体力、保留手牌、放大己方边际收益、通用压制、强化下一次压制和抵挡压制。早期关卡开放基础牌，后续按课程周次增加牌种。第一关使用下述教学卡池；其他关卡从已开放的槽位抽取两种设计措施，并混入一条至少存在理论可行解的设计路径；功能牌混入 8 张。W4 起保证有一张通用反制牌，W5 起再保证一张防护牌；通用反制消耗 1 点体力。整局牌组至多 20 张，双方牌组内容相同但各自独立洗牌；牌堆耗尽后循环弃牌。24 张措施卡与功能牌配置在 `src/course-config.json`；核心规则在 `src/game.ts`。玩家可查看本局牌组及“安装后仍有几条可达标路线”；路线考虑换装、已移除的牌和剩余安装轮次，不保证抽牌时机，计入已获得的永久优化，不预支尚未打出的优化牌或当轮减益。状态机也只用自己的牌组、手牌与公开方案规划可行路线。

## 第一关：采光教学关

第一关固定使用六张装置：适度扩大窗面、大面积窗面、固定外遮阳、可调外遮阳、浅进深布局、高反射内表面。双方牌组构成仍相同；学生起手保证两个不同槽位的可配合达标装置，以及一张“保留备选”，其余牌随机。发牌只交换原牌堆中的牌，不复制牌。先安装一张，再保留另一张，可以把起手优势延续到下一轮。

对手公开第一轮勘察，不安装、不反制、不使用功能牌；第二轮恢复正常决策。因此在该卡池下，对手最早第四轮完成三项装置。学生仍可第三轮获胜；五轮上限、体力和安装次数、同轮比较分数/预算的规则不变。性能门槛仍为 E≤120、D≥70、H≤180、C≤380，预算≤100，不能靠只堆采光或随便结束回合过关。

手牌标题旁显示当前还差哪些指标，选择装置时预览安装后的缺口，长提示可横向滑动。未中标会解释缺口；双方都达标时明确说明输在综合分或预算。后五关不应用教学规则，500 局固定种子对照确认其发牌、对手行动和结算与前一版本完全一致。

七种普通策略不读取对手手牌、隐藏抽牌顺序，也不搜索完整最优解；仅“按提示”使用界面已有的路线计数。这些策略不使用攻击，便于单独检验教学关的安装与保牌节奏。定稿后先用每种 1,000 局检查，再用未参与调参的 10,001–12,000 号种子、每种 2,000 局独立验证；新版共 21,000 局，旧版对照另 21,000 局。原始数据在 `validation/tutorial-training.json` 和 `validation/tutorial-holdout.json`。

这是脚本代理人的胜率，不是真人学生数据。随机选择仍明显更难赢，错过整轮仍会付出代价；保底起手不会保证获胜。测试脚本可用 `node scripts/tutorial-balance.mjs --runs=2000 --offset=10000` 复现。`npm test` 另验证 1,000 次起手的配套装置/保留牌、卡牌守恒、首轮勘察和不操作不能获胜。

## 为什么是 5、6、8 轮

| 关卡 | 上限 | 原因 |
| --- | ---: | --- |
| 采光、前期碳 | 5 | 目标通常靠 2–3 个关键因素形成可行方案；再给抽牌与反制空间。 |
| 能耗 | 6 | 需要兼顾采光和过热的副作用，给 1 轮额外缓冲。 |
| 采光与过热、综合设计、最终综合 | 8 | 六个设计槽位最多每轮安装一个；另外两轮容纳找牌、体力与攻防取舍。 |

这些都是**上限**，一方先达标会提前结束。换装规则加入前的版本用五种模拟策略、两批各 1000 个独立种子/关卡测试；规划型玩家的结束轮数中位数为采光 3、能耗 3、前期碳 4、采光与过热 5、综合 5、最终 5。复杂关卡第 90 百分位为 7 左右。模拟不能代表课堂耗时；真人试玩后还需按每轮思考时间和“无有效决策”的比例调整。

## 可玩性调参与模拟结果

聚焦优化现已改为永久增益，以下旧版及换装版的后期关卡胜率是历史结果。第一关没有聚焦优化牌，教学关数据仍对应当前规则。

以下 60,000 局表格为**禁止同槽换装的旧版基线**，不能直接作为当前版本胜率。第一关已进一步改为上述教学规则，旧表及换装回归不再代表当前第一关。换装版已经更新脚本的方案替换、路线筛选与对手意图预测逻辑，并另做两种策略各 200 局/关、共 2,400 局回归；结果记录在 `validation/replacement-balance.json`。脚本策略不等于真人学生。

目标是让**会规划并择时使用反制的玩家**在每关仍可能输，模拟胜率约 45%–65%；只看眼前数值的策略应明显更难赢。随机、眼前收益、新手按提示、规划路线、规划加攻防五种策略，在两个不重叠的随机种子批次上各打 1000 局/关，共 60,000 局。下表是第二批的**玩家获胜比例**，平局另算：

| 关卡 | 随机 | 只看眼前 | 按可行路线提示 | 规划路线 | 规划＋攻防 | 规划＋攻防平局 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| 采光 | 13.4% | 27.6% | 33.7% | 42.9% | 50.7% | 27.6% |
| 能耗 | 6.5% | 18.2% | 36.2% | 45.6% | 53.2% | 5.2% |
| 前期碳 | 4.1% | 22.4% | 36.9% | 45.4% | 54.4% | 1.2% |
| 采光与过热 | 4.1% | 13.9% | 30.1% | 46.1% | 56.7% | 3.9% |
| 综合设计 | 5.7% | 17.0% | 32.7% | 47.5% | 58.4% | 2.1% |
| 最终综合 | 3.1% | 11.1% | 36.4% | 46.3% | 57.1% | 3.4% |

这两个批次的每个策略/关卡胜率差至多约 3.4 个百分点。后期关卡的攻防策略每局平均打出约 0.28–0.33 次反制，对手公开 PRESSURE 意图约 0.47–0.63 次；两边合计接近每局一次攻防机会。采光入门关的完全相同方案仍会产生较多平局，因此平局会记录为“设计达标”，但不算竞标胜利。

上述策略都是脚本代理人：随机策略乱选，眼前策略只看当前缺口，提示策略会避开使可行路线归零的措施，规划策略从可用卡组找可达标组合，攻防策略还会择时抽牌、保牌、增益、反制与防护。它们不是学生能力分组，也不能证明真人会觉得好玩。真人试玩应记录胜率、平均决策时间、误解指标的次数、主动反制次数和重开原因，再调整卡池与状态机。两批原始结果保留在课程研究工作区，未包含在这个独立演示仓库中。

## 数值来源与边界

四项代理指标为 E（能耗）、D（采光）、H（过热小时）、C（A1–A5 前期碳），基准分别为 100、45、160、300。24 张措施卡的增量、四组交互效应和关卡权重来自课程研究工作区先前建立的**合成教学算例**；试玩后调整了采光、能耗、前期碳关的门槛（以 `src/course-config.json` 为准）。它们不是 M-huset 的实测值、仿真结果或合规标准。预算 100 是游戏点数。课程任务书中的扩建面积上限 1500㎡是课程约束；本代理模型并不生成几何。

正向边际收益按 `F(当前方案) − F(移除该措施后的方案)` 计算，包括措施间交互。聚焦优化对指定装置的指定有利指标永久 +25%（本局内），换轮保留；同装置同指标不能叠加，不同指标可分别优化。拆除旧装置会清除其优化，新一局不继承。压制只持续当轮。二者修正**竞标评审值**，不篡改界面显示的原始物理代理值。E/H/C 越低越好，D 越高越好。加权分使用固定归一化：E 对应 120→50、D 对应 30→80、H 对应 200→50、C 对应 400→200，指标分限制在 0–100；门槛必须先全部通过，分数只做同轮达标时的裁决。

进入真实课程项目时，需用同一基准模型和课程工具重新标定卡片增量与交互；保留来源、单位、工况和不确定性。当前数值只用于测试“不同委托下该看哪些因素和指标”的玩法。

## 验证

永久优化回归：`scripts/permanent-buff.mjs` 验证连续换轮、同指标封顶、不同指标分别优化、临时压制到期、双方规则一致、拆除/新局清理，以及带优化的可行路线。`scripts/permanent-buff-ui.mjs` 在 568×320、844×390、390×844 和 1440×900 实际点击优化并连续换轮，核对 HUD 数值、标记和换装。两种规划策略各 200 局/关、共 2,400 局的规则回归结果见 `validation/permanent-optimization-regression.json`，新增了永久优化不能重复叠加的断言；这不是一次新的真人难度标定。

`npm test` 先检查换装体力与次数、预算返还、旧联动移除、压制/增益/护盾清理、旧牌不循环、剩余路线和 NPC 换装防御，再检查六关均有理论可行解、预算不超标、交互被计入边际收益、反制只改变评审值、体力牌与同名反制的行为、200 个固定种子下每关均能在上限内结束。`node --experimental-strip-types scripts/playability.mjs --runs=1000` 会运行五种模拟玩家策略，每关各 1000 局并检查预算、槽位、手牌、体力与轮数不变量。浏览器脚本检查 1920px、1366px 与 390px 视口能进入关卡、查看牌组、选择手牌、结束回合，且无运行错误和横向页面溢出。
