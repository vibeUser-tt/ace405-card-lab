# ACE405 建筑竞标实验室

学生与有限状态机对手竞标同一建筑设计委托的 Web 卡牌原型。原来的“余烬之塔”两场打怪系统已替换为建筑性能指标、措施卡、功能卡和单人对抗流程。每个关卡对应课程周次与不同的目标函数；没有学生之间的对战。

## 运行

需要 Node.js 20.19+ 或 22.12+。

```powershell
cd ace405-card-lab
npm install
npm run dev
```

打开终端给出的本地地址，通常为 http://127.0.0.1:5173/。运行 `npm run build` 构建静态网页；运行 `npm test` 执行规则测试和固定种子模拟。桌面与手机浏览器交互测试脚本为 `node scripts/ui-smoke.mjs`，需本地 Vite 服务、Playwright 与 Chrome。

## 发布到 GitHub Pages

这个 `demo` 目录是独立仓库的根目录。仓库的 `main` 分支推送后，`.github/workflows/deploy.yml` 会构建 `dist` 并发布。Vite 使用相对资源路径，因此普通项目仓库和 `<用户名>.github.io` 仓库都可使用。

1. 在 GitHub 创建空仓库，不勾选初始化 README、`.gitignore` 或 License；将本目录推送到 `main`。
2. 在仓库 **Settings → Pages → Build and deployment → Source** 选择 **GitHub Actions**。
3. 等待 **Actions → Deploy to GitHub Pages** 成功后，从 Pages 设置页打开网站。普通仓库地址为 `https://<用户名>.github.io/<仓库名>/`。

GitHub Pages 是公开网页。当前游戏记录只保存在访问者自己的浏览器中，不会跨设备同步。

## 3D 战场与手机适配

主界面采用单个 Three.js Canvas，双方各有一栋程序化建筑。六类装置对应窗、外墙、遮阳、屋顶布局、材料表皮和系统设备；24 张措施牌都有对应模型变体。热回收有双路气流，夜间通风有通风口，按需控制有控制面板，采光联动照明有灯带。方向光、半球光和阴影提供体积感。

安装牌触发装配粒子；反制从手牌位置飞向目标部件，命中后出现碎片、冲击环和本轮裂纹标记；护盾显示保护网格。模型是教学示意，性能指标仍由规则模型计算。点击 HUD 可查看原始值、评审值和权重；点击建筑装置可选取增益或反制目标。

布局根据 `visualViewport` 的实际宽高判断：宽大于高时，选牌在右侧打开独立操作栏，战场预留相应宽度；竖屏在下方手牌区内打开面板，上方继续显示双方建筑。窗口调整、手机旋转和浏览器工具栏改变可用高度时会重新计算，保留当前局与所选目标。详情在面板内部滚动，确认按钮独立固定；聚焦筛选与保留备选直接高亮手牌供选择，不打开操作面板：弃牌单选，保留选择 1–2 张，选好后才可确认；再次点击发动牌或取消按钮会退出且不消耗资源。界面预留刘海与底部手势安全区。

32 张牌均有成功出牌反馈。玻璃、围护、遮阳、布局、材料与系统的安装粒子使用不同形状和颜色，装置从目标位置组装出现；反制命中对应部件。八种功能牌分别显示抽牌、弃抽、体力、保留、增益、干扰、强化与护盾反馈。保留标记与待用反制强化持续显示，粒子落点按面板关闭后的布局计算；未满足条件的牌不播放成功特效。减少动态效果偏好会关闭飞行粒子，保留文字结果。

`npm run test:ui` 要求本地 Vite 服务、Chrome、Playwright 与支持 TypeScript stripping 的 Node（当前测试为 Node 24）。视口覆盖 568×320、667×375、740×320、844×390、932×430、1024×768、1440×900，以及 360×640、390×844、430×932；检查选牌面板不与建筑区域相交、操作按钮在屏内、旋转后选择不丢失、模拟安全区、32 张牌特效及全部模型变体。`complete-games.mjs` 用触控事件在 667×375、844×390、390×844 各从开局打完两局，覆盖安装、同名反制、功能牌与三种结算结果。六局固定种子样例为 1 胜、4 负、1 平，是交互回归样例，不是平衡性胜率估计。测试使用桌面浏览器模拟触控视口，实际手机 GPU 性能及 iOS 应用内浏览器仍需真机体验。

## 每局如何玩

1. 选择课程关卡，阅读四项指标门槛、预算上限与公开权重。
2. 每轮抽 5 张牌、获得 3 点基础体力；安装至多 1 张措施、反制至多 1 次、使用至多 2 张功能牌。体力牌可将本轮体力提升到 5。
3. 措施卡可以装到自己的方案。如果对手已经安装同名措施，也可以消耗这张手牌反制对手一个**有正向边际收益的指标**。同名反制削减该收益 50%，通用反制牌削减 25%。反制牌从本局移除。
4. 状态机在学生行动前公开本轮意图。它只使用自己的手牌、双方公开方案和公开目标函数，按 SECURE → PRESSURE → BUILD → REFILL 的优先级作决策。
5. 结束回合时，对手执行行动，然后双方同时评审。先通过全部四项性能门槛与预算门槛的一方获胜；同轮都通过时比较公开加权分、再比较预算；仍相同则平局。
6. 每局结束有回合复盘。课程关卡均可从入口选择；本地浏览器会记住各关卡最快的**达标**轮数。平局仍表示学生方案达标，但不算竞标胜利。游戏成绩不替代课程作业评价。

八种功能牌分别负责抽牌、弃抽、补体力、保留手牌、放大己方边际收益、通用压制、强化下一次压制和抵挡压制。早期关卡开放基础牌，后续按课程周次增加牌种。每局从已开放的槽位抽取两种设计措施，并混入一条至少存在理论可行解的设计路径；功能牌混入 8 张。W4 起保证有一张通用反制牌，W5 起再保证一张防护牌；通用反制消耗 1 点体力。整局牌组至多 20 张，双方牌组内容相同但各自独立洗牌；牌堆耗尽后循环弃牌。24 张措施卡与功能牌配置在 `src/course-config.json`；核心规则在 `src/game.ts`。玩家可查看本局牌组及“安装后仍有几条可达标路线”，防止不知情地把方案锁死。状态机也只用自己的牌组、手牌与公开方案规划可行路线。

## 为什么是 5、6、8 轮

| 关卡 | 上限 | 原因 |
| --- | ---: | --- |
| 采光、前期碳 | 5 | 目标通常靠 2–3 个关键因素形成可行方案；再给抽牌与反制空间。 |
| 能耗 | 6 | 需要兼顾采光和过热的副作用，给 1 轮额外缓冲。 |
| 采光与过热、综合设计、最终综合 | 8 | 六个设计槽位最多每轮安装一个；另外两轮容纳找牌、体力与攻防取舍。 |

这些都是**上限**，一方先达标会提前结束。最终版用五种模拟策略、两批各 1000 个独立种子/关卡测试；规划型玩家的结束轮数中位数为采光 3、能耗 3、前期碳 4、采光与过热 5、综合 5、最终 5。复杂关卡第 90 百分位为 7 左右。模拟不能代表课堂耗时；真人试玩后还需按每轮思考时间和“无有效决策”的比例调整。

## 可玩性调参与模拟结果

目标是让**会规划并择时使用反制的玩家**在每关仍可能输，模拟胜率约 45%–65%；只看眼前数值的策略应明显更难赢。随机、眼前收益、新手按提示、规划路线、规划加攻防五种策略，在两个不重叠的随机种子批次上各打 1000 局/关，共 60,000 局。下表是第二批的**玩家获胜比例**，平局另算：

| 关卡 | 随机 | 只看眼前 | 按可行路线提示 | 规划路线 | 规划＋攻防 | 规划＋攻防平局 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| 采光 | 13.4% | 27.6% | 33.7% | 42.9% | 50.7% | 27.6% |
| 能耗 | 6.5% | 18.2% | 36.2% | 45.6% | 53.2% | 5.2% |
| 前期碳 | 4.1% | 22.4% | 36.9% | 45.4% | 54.4% | 1.2% |
| 采光与过热 | 4.1% | 13.9% | 30.1% | 46.1% | 56.7% | 3.9% |
| 综合设计 | 5.7% | 17.0% | 32.7% | 47.5% | 58.4% | 2.1% |
| 最终综合 | 3.1% | 11.1% | 36.4% | 46.3% | 57.1% | 3.4% |

这两个批次的每个策略/关卡胜率差至多约 3.4 个百分点。后期关卡的攻防策略每局平均打出约 0.28–0.33 次反制，对手公开 PRESSURE 意图约 0.47–0.63 次；两边合计接近每局一次攻防机会。采光入门关的完全相同方案仍会产生较多平局，因此平局会记录为“设计达标”，但不算竞标胜利。

上述策略都是脚本代理人：随机策略乱选，眼前策略只看当前缺口，提示策略会避开使可行路线归零的措施，规划策略从可用卡组找可达标组合，攻防策略还会择时抽牌、保牌、增益、反制与防护。它们不是学生能力分组，也不能证明真人会觉得好玩。真人试玩应记录胜率、平均决策时间、误解指标的次数、主动反制次数和重开原因，再调整卡池与状态机。两批原始结果保留在课程研究工作区，未包含在这个独立演示仓库中。

## 数值来源与边界

四项代理指标为 E（能耗）、D（采光）、H（过热小时）、C（A1–A5 前期碳），基准分别为 100、45、160、300。24 张措施卡的增量、四组交互效应和关卡权重来自课程研究工作区先前建立的**合成教学算例**；试玩后调整了采光、能耗、前期碳关的门槛（以 `src/course-config.json` 为准）。它们不是 M-huset 的实测值、仿真结果或合规标准。预算 100 是游戏点数。课程任务书中的扩建面积上限 1500㎡是课程约束；本代理模型并不生成几何。

正向边际收益按 `F(当前方案) − F(移除该措施后的方案)` 计算，包括措施间交互。压制与增益只修正**本轮竞标评审值**，不篡改界面显示的原始物理代理值。E/H/C 越低越好，D 越高越好。加权分使用固定归一化：E 对应 120→50、D 对应 30→80、H 对应 200→50、C 对应 400→200，指标分限制在 0–100；门槛必须先全部通过，分数只做同轮达标时的裁决。

进入真实课程项目时，需用同一基准模型和课程工具重新标定卡片增量与交互；保留来源、单位、工况和不确定性。当前数值只用于测试“不同委托下该看哪些因素和指标”的玩法。

## 验证

`npm test` 检查六关均有理论可行解、预算不超标、交互被计入边际收益、反制只改变评审值、体力牌与同名反制的行为、200 个固定种子下每关均能在上限内结束。`node --experimental-strip-types scripts/playability.mjs --runs=1000` 会运行五种模拟玩家策略，每关各 1000 局并检查预算、槽位、手牌、体力与轮数不变量。浏览器脚本检查 1920px、1366px 与 390px 视口能进入关卡、查看牌组、选择手牌、结束回合，且无运行错误和横向页面溢出。
